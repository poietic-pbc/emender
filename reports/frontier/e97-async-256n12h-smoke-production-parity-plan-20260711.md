# E97 async 256-node smoke/production parity audit and hard-gate plan

Date: 2026-07-11  
Task: `audit-e97-async-256`  
Decision: **NO-GO for any further 256n12h submission until an exact-bundle
256-node smoke is promoted through the gate defined below.**

## Executive finding

The successful smoke and failed production job were not two scheduler profiles
of one run. They were separate launch stacks reconstructed by hand.

- Smoke job `4962400` completed at `256` nodes / `2048` GPU ranks, accepted
  `2048/2048` updates, and reported loss `2.52083`. Its evidence is in
  `reports/frontier/async-quorum-b4k40-debug-ladder-20260709.md` and its fully
  expanded command is
  `/lustre/orion/bif148/proj-shared/emender/frontier_runs/debug/async_quorum_b4k40_ladder_20260709/20260709/E97_1.3B_step1065000_async_quorum_b4k40_ladder_256n/4962400-20260709T144830Z/artifacts/command.txt`.
- Production job `4963853` failed before training with
  `ValueError: node_rank must be in [0, node_count)`. Its handoff is
  `reports/frontier/e97-async-256n12h-rank-count-failure-handoff-20260711.md`;
  its expanded command is
  `/lustre/orion/bif148/proj-shared/emender/frontier_runs/async_diloco/E97_1.3B_step1282500_async_quorum_b4_k40_256n12h/20260711/4963853-20260711T115539Z/artifacts/command.txt`.

The immediate exception is exact: production launched ranks `0..2047` but
passed `--node-count 256`; `scripts/frontier/e97_async_diloco_train.py` derives
an omitted `--node-rank` from `SLURM_PROCID`, and
`ndm/async_diloco_real.py` rejects rank `>= node_count`. Smoke passed both
`--node-count 2048` and an explicit per-process
`--node-rank "$SLURM_PROCID"`. The deeper cause is the absence of a canonical,
immutable run specification and parity gate: production used
`scripts/frontier/async_diloco_e97_256n12h_launch.sbatch`, while smoke used
`scripts/frontier/trainpy_async_quorum_2n_smoke.sbatch` plus
`scripts/frontier/trainpy_async_quorum_smoke_common.sh`.

## Strict difference policy

This audit applies the user's corrected policy, which supersedes broader
"routing" wording in the original task description.

Only these fields may differ:

1. Job duration: Slurm walltime and the corresponding trainer duration/stop
   budget, provided the latter is a deterministic derivation of walltime.
2. Queue selection: partition and QoS only when they are the site's concrete
   representation of selecting the smoke versus production queue.

Nothing else is allowed to differ. In particular, account and reservation are
**not** independent routing overrides. Account, reservation, node count, rank
count, tasks/ranks per node, CPU/GPU binding, model/data/optimizer/DiLoCo
configuration, seed checkpoint identity and bytes, environment, modules,
container/conda prefix, launcher, entrypoint, helper, code revision, argv,
non-scheduler environment, output/publication policy, and approval-independent
runtime behavior must be byte-for-byte or canonically equal. Job name, log/run
paths, job/task IDs, timestamps, allocated hostnames, and rendezvous port may be
derived metadata, never profile inputs; the comparator normalizes their
declared placeholders only after proving they were generated by the same
renderer.

`#SBATCH -A bif148` happens to match and must continue to match. A production
account change would fail the gate. Neither profile may add a reservation.

The exact smoke command begins:

The exact production command begins:

Thus changing only production `--node-count` would remove the observed

seed, revision, launcher, model alias, memory, timeout, and durability changes.

## Canonical run specification

Create one immutable, versioned bundle, for example
`configs/frontier/e97_async_256.yaml`, consumed by one renderer and one sbatch
template. It must contain every non-queue/non-duration field: repository commit
and clean-tree requirement; seed/data/tokenizer content hashes; runtime/module
and helper build hashes; `256 x 8` topology; exact entrypoint and launch shell;
resolved model, optimizer, DiLoCo, transport, checkpoint/publication settings;
and validation thresholds. Prefer the **known successful `4962400` resolved
specification** as the initial canonical payload. Do not mix it with selected
production settings. Any desired algorithmic or seed update starts a new
canonical bundle and must earn a new 256-node smoke.

Profiles contain exactly:

```yaml
profiles:
  smoke:
    walltime: "00:20:00"
    queue: {partition: batch, qos: debug}
  production:
    walltime: "12:00:00"
    queue: {partition: batch, qos: normal}
```

The schema rejects unknown profile keys. Account remains in the canonical base
(`bif148`), not either profile. Reservation is canonically absent. The renderer
emits a self-contained bundle containing `rendered.sbatch`, `runtime.json`
(resolved argv and sorted allowlisted env), `inputs.json` (realpath, size,
SHA256), `code.json`, and `fingerprint.sha256`. Both jobs submit that same
content-addressed bundle; production is never reconstructed from YAML or shell
arguments after smoke.

## Executable fail-closed parity gate

Implement `scripts/frontier/render_e97_async_256.py` and
`scripts/frontier/check_e97_async_promotion.py`. The renderer must have a
side-effect-free `--render-only`; the check should be runnable as:

```bash
python scripts/frontier/render_e97_async_256.py --profile smoke --out build/e97-256/smoke
python scripts/frontier/render_e97_async_256.py --profile production --out build/e97-256/production
python scripts/frontier/check_e97_async_promotion.py \
  --smoke build/e97-256/smoke --production build/e97-256/production \
  --policy configs/frontier/e97_async_256_parity_policy.json
```

The checker parses rather than text-deletes fields. It must:

1. Parse all `#SBATCH` directives into canonical keys; allow unequal values
   only for `time`, `partition`, and `qos`. Reject unequal/missing account,
   reservation, constraints, topology, binding, output behavior, dependency,
   signal/requeue, export policy, or any unknown directive.
2. Replace the three allowed scheduler values with typed sentinels and compare
   the complete rendered scripts byte-for-byte. Job/profile labels and output
   paths must be renderer-derived placeholders, not ignored arbitrary text.
3. Compare canonical JSON of the fully resolved trainer argv, `srun` argv,
   sorted runtime env, module list, Python executable/environment manifest,
   helper build manifest, git commit/tree hash, and hashed inputs. No runtime
   env key is generically ignored. Only scheduler-injected ephemeral values
   explicitly declared by the renderer (`SLURM_JOB_ID`, host list, timestamp,
   derived run ID/path/port) are replaced with sentinels and their derivation
   rules are tested.
4. Require invariants: physical nodes `256`; ranks/node `8`; launched,
   participant, worker, global-quorum, and rank-start expectation all `2048`;
   unique rank IDs `0..2047`; one GPU per rank; and no unresolved `${...}`.
5. Hash canonical normalized sbatch + runtime JSON + input/code/runtime/helper
   manifests. Exit nonzero with a JSON diff for any forbidden difference.
6. Refuse submission unless production carries the exact promoted smoke
   fingerprint and a signed/atomic `promotion.json` naming the completed Slurm
   job, artifact paths, `COMPLETED 0:0`, `2048/2048` starts and accepted
   updates, finite loss/merge, metrics, checkpoint reload, and no external
   pointer mutation.

Unit fixtures must prove one passing walltime/QoS change and individually
failing mutations for account, reservation, node/rank/GPU topology, seed,
data, model, optimizer, quorum, timeout, environment/module, launcher,
entrypoint, revision, helper hash, and checkpoint policy. A checked-in golden
render pair makes this a CI/pre-submit gate, not a convention.

## Smoke promotion procedure (no reconstruction)

1. Pin a clean commit, resolve symlinks, hash all inputs and runtime artifacts,
   render both profiles, and pass the parity checker before allocation.
2. Atomically publish the content-addressed bundle read-only. Submit its smoke
   `rendered.sbatch`; no `--export` recipe overrides are permitted.
3. On the real 256-node allocation, capture the resolved argv/env/module/input
   manifests again and compare to the bundle **before `srun`**. Abort on drift.
4. Accept the smoke only on `COMPLETED 0:0`, exactly `2048/2048` unique rank
   starts and updates, finite loss, at least one completed DiLoCo merge,
   expected transport, metrics/manifest, finalized checkpoint plus successful
   reload, and unchanged external production pointer.
5. The validator writes `promotion.json` into that same immutable bundle and
   records the bundle fingerprint. It does not create a new production config.
6. Production submission reads the promoted bundle by fingerprint, re-renders
   only the typed duration/queue fields, runs the parity check again, verifies
   seed/code/runtime hashes have not changed, and submits. Any change or expired
   input invalidates promotion and returns to step 1.
7. At production start, repeat the on-node preflight. Archive the final
   `scontrol show job`, rendered script, argv/env, and fingerprint with the run.

   remain identical. A real submission requires the separate human approval

4. `quality-pass-e97` and `.flip-audit-e97-async-256` should review this report
   and the task specifications, not reimplement them. Existing historical
   ladder/evaluation tasks remain evidence only; they cannot substitute for
   the exact-bundle smoke because their launcher and fingerprint differ.

The smallest robust change is therefore not another production-wrapper patch.
It is to delete the independent production recipe as an authority, render both
profiles from the proven smoke specification, and make the immutable successful
smoke fingerprint the sole production submission input.
